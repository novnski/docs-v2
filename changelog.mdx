<Update label="August 26, 2026" tags={["Deprecation"]}>
  ## Lisk Support Removed: September 25, 2026

  Moralis support for **Lisk** (`0x46f` / 1135) is removed on **September 25, 2026**, across the Data API, Streams, RPC Nodes, and Datashare.

  **Why:** Lisk is winding down the Lisk Chain as part of [the next chapter for Lisk](https://lisk.com/blog/posts/introducing-the-new-lisk/). The LSK token contract on Ethereum is unchanged, and Base becomes LSK's primary network alongside Ethereum, so ongoing activity moves to two chains Moralis already covers in full.

  **Timeline**

  | Date | State |
  | --- | --- |
  | September 25, 2026 | Moralis removes Lisk support. Requests targeting `lisk` / `0x46f` return an unsupported-chain error |
  | October 31, 2026 | Lisk's deadline for users to bridge assets from the Lisk Chain to Ethereum. Lisk notes that bridging takes at least 7 days, so start before late October 2026 |
  | November 30, 2026 | Final shutdown of the Lisk Chain and its related infrastructure |

  Note that Moralis removes support ahead of Lisk's own dates. The Lisk Chain keeps producing blocks and its infrastructure keeps running as normal until November 30, 2026. If you need chain access between September 25, 2026 and that date, point your integration at Lisk's own endpoints. See the [Lisk documentation](https://docs.lisk.com/), which stays available.

  **What changes on September 25, 2026**

  - **Data API:** wallet, token, NFT, entity, and blockchain endpoints reject `lisk` and `0x46f`. This applies to the `chain` query parameter on Deep Index endpoints and to the `chains` array on Universal API endpoints, so remove the value from your chain lists rather than relying on the rest of a multi-chain request still resolving.
  - **RPC Nodes:** `https://site1.moralis-nodes.com/lisk/` and `https://site2.moralis-nodes.com/lisk/` stop resolving, including archive reads at historical block heights. The Lisk RPC reference pages are removed from the navigation.
  - **Streams:** any stream that still lists `0x46f` in `chainIds` is invalid. List your streams with [Get streams](/streams/api-reference/streams/get-streams), then either [update the stream](/streams/api-reference/streams/update-stream) to a supported chain or [delete it](/streams/api-reference/streams/delete-stream).
  - **Datashare:** Lisk is removed from the available datasets.

  Lisk Sepolia (`0x106a` / 4202) was already removed in the [June 15, 2026 testnet wind-down](#testnets-removed).

  **Export your history before September 25, 2026**

  If you still need Lisk Chain data from Moralis, pull it while the endpoints answer. Paginate each call with `cursor` until the response returns an empty `result` and no `cursor`.

  | Data | Endpoint |
  | --- | --- |
  | Full wallet history, decoded | [Wallet History](/data-api/evm/wallet/wallet-history) |
  | ERC-20 transfers | [Wallet Token Transfers](/data-api/evm/wallet/token-transfers) |
  | NFT transfers | [Wallet NFT Transfers](/data-api/evm/wallet/nft-transfers) |
  | Closing token balances | [Wallet Token Balances](/data-api/evm/wallet/token-balances) |

  **Where to point your integration**

  | Network | Data API chain value | RPC path |
  | --- | --- | --- |
  | Ethereum | `eth` (`0x1`) | `https://site1.moralis-nodes.com/eth/` |
  | Base | `base` (`0x2105`) | `https://site1.moralis-nodes.com/base/` |

  Both are fully supported across the Data API, RPC Nodes, and Streams. Your API key, authentication, request shapes, and response formats do not change. Only the target chain does.

  If you hold LSK on Ethereum or on an exchange, the token contract is unchanged and no action is needed. If you hold LSK on the Lisk Chain, bridge it to Ethereum before October 31, 2026.

  For questions about the Lisk Chain itself, Lisk's [documentation](https://docs.lisk.com/) remains available and user-facing support has moved to [support.lisk.com](https://support.lisk.com/). If this change affects your Moralis integration or you need additional time, [reach out to the team](https://admin.moralis.com/) (via chat widget).
</Update>

  ## Moonbeam and Moonriver Historical Data Removal: September 25, 2026

  On **August 21, 2026** Moralis stopped serving real-time **Moonbeam** (`0x504`) and **Moonriver** (`0x505`) data. Historical data was left in place, so read requests kept returning records up to the last indexed block on each chain.

  That ends on **September 25, 2026**. After this date, historical Moonbeam and Moonriver data is removed and no longer available through any Moralis product.

  **Why:** GLMR and MOVR migrated to Base as 1:1 ERC-20 tokens ([Moonbeam](https://moonbeam.network/news/moonbeam-strategic-update-moonbeam-network-relaunches-on-base/), [Moonriver](https://moonbeam.network/news/moonriver-strategic-update-movr-is-migrating-to-base/)), holder bridging closed on July 31, 2026, and both original networks stopped producing blocks. There is no new state left to index on either chain.

  **Timeline**

  | Date | State |
  | --- | --- |
  | July 31, 2026 | Holder bridging to Base closed |
  | August 21, 2026 | Real-time support removed. Streams stopped emitting webhooks and responses stopped advancing, since no new blocks were being produced |
  | September 25, 2026 | Historical support removed. Requests targeting these chains return an unsupported-chain error |

  **What changes on September 25, 2026**

  - **Data API:** wallet, token, NFT, DeFi, and price endpoints reject `moonbeam`, `0x504`, `moonriver`, and `0x505`. This applies to the `chain` query parameter on Deep Index endpoints and to the `chains` array on Universal API endpoints, so remove these values from your chain lists rather than relying on the rest of a multi-chain request still resolving.
  - **RPC Nodes:** `https://site1.moralis-nodes.com/moonbeam/`, `https://site2.moralis-nodes.com/moonbeam/`, and the matching `moonriver` paths stop resolving. Archive reads at historical block heights (`eth_getBlockByNumber`, `eth_getLogs`, `eth_getBalance` with a past block tag) go with them.
  - **Streams:** any stream that still lists `0x504` or `0x505` in `chainIds` is invalid. List your streams with [Get streams](/streams/api-reference/streams/get-streams), then either [update the stream](/streams/api-reference/streams/update-stream) to `["0x2105"]` or [delete it](/streams/api-reference/streams/delete-stream).
  - **Docs:** the Moonbeam and Moonriver RPC reference pages and their chain rows in the supported-chains tables are removed from the navigation.

  **Export your history before September 25, 2026**

  If you still need this data, pull it while the endpoints answer. Paginate each call with `cursor` until the response returns an empty `result` and no `cursor`.

  | Data | Endpoint |
  | --- | --- |
  | Full wallet history, decoded | [Wallet History](/data-api/evm/wallet/wallet-history) |
  | ERC-20 transfers | [Wallet Token Transfers](/data-api/evm/wallet/token-transfers) |
  | NFT transfers | [Wallet NFT Transfers](/data-api/evm/wallet/nft-transfers) |
  | Closing token balances | [Wallet Token Balances](/data-api/evm/wallet/token-balances) |

  **Migrating to Base**

  GLMR, MOVR, and all associated activity are tracked on Base going forward. Your API key, authentication, request shapes, and response formats do not change. Only the target chain does.

  - **Data API:** set the chain to `base` (`0x2105`).
  - **RPC Nodes:** swap the path segment to `https://site1.moralis-nodes.com/base/`. See the [Base RPC reference](/rpc-nodes/base/overview).
  - **Streams:** create the stream with `"chainIds": ["0x2105"]` and the Base contract addresses below.

  | Token | Contract address on Base |
  | --- | --- |
  | GLMR | `0xb3846fd356c2149ee8d30b0449088dc74e265459` |
  | MOVR | `0x43fEB74608334DDa8c1a6500D185cFC3Ea962B83` |

  For a walkthrough of the migration, watch [Moonbeam and Moonriver Migration to Base](https://www.youtube.com/watch?v=63UJ4EaqfUM).

  If this change affects your integration or you need additional time, [reach out to the team](https://admin.moralis.com/) (via chat widget).

<Update label="July 21, 2026" tags={["New Feature"]}>
  ## Cross-Chain Token Balances

  One of our most popular Deep Index endpoints, **Token Balances**, is now available on the Universal API as **Cross-Chain Token Balances**. A single request returns a wallet's token balances across multiple chains - no more one-request-per-chain plus client-side stitching.

  **What changed vs. the legacy endpoint:**

  |  | Legacy ([getWalletTokenBalancesPrice](https://deep-index.moralis.io/api-docs-2.2/#/Wallets/getWalletTokenBalancesPrice)) | New ([getTokenBalances](https://api.moralis.com/api#/Wallets/getTokenBalances)) |
  | --- | --- | --- |
  | Scope | Single chain per request | Multi-chain in one request |
  | Chain coverage | EVM | EVM + Bitcoin (Solana coming) |
  | Filters | Spam exclusion, unverified contracts, liquidity thresholds, etc. | All preserved |
  | Pricing data | Included | Included, plus optional `includeSparklines` and `includePnl` enrichment per token |

  Everything customers already rely on - spam filtering, unverified contract exclusion, liquidity thresholds, USD pricing - works exactly the same. The only difference is you can now ask for multiple chains in a single call.

  **Who it's for:** wallets, exchanges, portfolio dashboards, tax tools, and AI agents that need a wallet's full multi-chain holdings without firing one request per chain.

  **Why it matters:**

  - **Fewer requests, simpler integration** - one call instead of N (where N = chains your users hold assets on)
  - **Faster portfolio views** - no client-side stitching across responses
  - **Same trusted filters** - spam, unverified, and low-liquidity controls carry over unchanged, so existing implementations port cleanly

  **Roadmap:** covers EVM and Bitcoin (address or xpub) today. Coming next:

  - **Solana** - Solana token balances brought into the Universal API (we already offer Solana token balances as a dedicated API; this unifies them into the same multi-chain request structure)

  The end state: one endpoint, one request shape, balances across EVM, Bitcoin, and Solana wallets.

  [Try the new endpoint →](https://api.moralis.com/api#/Wallets/getTokenBalances)
</Update>

<Update label="July 18, 2026" tags={["New Feature"]}>
  ## Token Price Timeseries & Sparkline

  Two chart-ready price endpoints are now available on the Universal API, covering native coins and tokens across EVM (Ethereum, Base, BNB, Polygon, Arbitrum, Linea, and more), Solana, and Bitcoin - through a single request shape.

  - **[Token Price Timeseries](/data-api/universal/token/price/token-price-timeseries)** ([getTokenPriceTimeSeries](https://api.moralis.com/api#/Tokens/getTokenPriceTimeSeries)) - historical price points for a token at your chosen `interval` (`5m` up to `monthly`), with optional forward-fill for gap-free line charts.
  - **[Token Price Sparkline](/data-api/universal/token/price/token-price-sparkline)** ([getTokenPriceSparkline](https://api.moralis.com/api#/Tokens/getTokenPriceSparkline)) - a fixed number of price points for a selected `range` (`24h` to `1y`) - drop the response directly into a sparkline widget in token lists, watchlists, or portfolio rows, no resampling needed.

  **Who it's for:** wallets, portfolio dashboards, token screeners, and trading UIs that need price charts without building candle-aggregation pipelines.

  [Try the new endpoints →](https://api.moralis.com/api#/Tokens)
</Update>

  ## Multi-Chain PnL Endpoints

  Wallet profitability is now available on the Universal API as a dedicated **[PnL API](/data-api/universal/pnl/overview)** - three new endpoints that replace the legacy single-chain Deep Index profitability endpoints with **multi-chain requests**:

  | New (Universal) | Replaces (Deep Index) |
  | --- | --- |
  | [Wallet PnL](/data-api/universal/pnl/wallet-pnl) - per-token realized/unrealized PnL, ROI, volumes, and trade counts across multiple chains | [Wallet PnL Breakdown](/data-api/evm/wallet/wallet-pnl) |
  | [Wallet PnL Summary](/data-api/universal/pnl/wallet-pnl-summary) - aggregated wallet-level totals including win rate | [Wallet PnL Summary](/data-api/evm/wallet/wallet-pnl-summary) |

  ## Fantom Chain Sunsetting

  Fantom mainnet support is being removed across all Moralis APIs on **May 29, 2026**. Fantom Opera testnet has already been removed. The Fantom Opera network is winding down as a legacy chain, and we're retiring our integration in line with the broader ecosystem shift.

  - **Streams** — existing Fantom streams will stop emitting webhook notifications and should be deleted from your workspace.
  - **Testnet** — Fantom Opera testnet was removed ahead of mainnet as part of this wind-down.

  **Why:** Fantom Opera has transitioned into a legacy chain with declining activity following the broader migration to Sonic. Maintaining a dedicated integration is no longer justified by usage, so we're consolidating support onto actively maintained networks.

  **What to do:**

  - Remove any `fantom` / `0xfa` references from your API requests, SDK calls, and stream configurations before May 29 to avoid errored responses.
  - If you still rely on Fantom data, migrate to an alternative provider, or move your workloads to one of the [supported chains](/data-api/supported-chains).

  All other supported chains are unaffected.
</Update>

<Update label="May 14, 2026" tags={["New Feature"]}>
  ## Mempool Notifications for Bitcoin Streams

  Bitcoin Streams now emit webhook notifications for **unconfirmed transactions** as soon as they hit the mempool — no need to wait for block inclusion.

  **What's new:**

  - **Pre-confirmation delivery** — matching transactions fire a webhook the moment they are broadcast to the mempool
  - **Same payload shape** as a confirmed-block webhook, with sentinel fields on the `block` object marking the delivery as mempool:
    - `block.height` → `"0"`
    - `block.hash` → `"mempool"`
    - `confirmed` → `false`
  - **`vin` and `vout` addresses both populated** in mempool payloads, so a watched address triggers a match whether it is sending or receiving
  - **Xpub-derived addresses fully supported**

  **Behavior to plan around:**

  - Each mempool transaction is delivered **at most once per stream**
  - The mempool delivery has **no follow-up** — the regular confirmed-block stream (`confirmed: false` then `confirmed: true`) handles in-block and reorg-safe deliveries for the same `txid`
  - Mempool transactions are **not guaranteed to confirm** — they can be replaced (RBF), evicted, or expire on low fee. Treat them as pending, not settled

  **Use cases:** show users a pending balance the instant a tx is broadcast, trigger UX flows on payment broadcast instead of confirmation, mempool monitoring, RBF detection, fee analytics, and MEV / arbitrage signals.

  No new endpoint, parameter, or schema. Existing Bitcoin streams pick this up automatically — branch on `block.hash === "mempool"` in your webhook handler to separate mempool events from confirmed-block events. See the [Mempool Notifications](/streams/bitcoin-streams#mempool-notifications) section for the full payload and handler patterns.

  [Explore Bitcoin Streams →](/streams/bitcoin-streams)
</Update>

  ## Bitcoin Streams

  Moralis Streams now extends to Bitcoin mainnet. Define a stream, attach the addresses or xpubs you want to watch, and receive real-time webhook deliveries within seconds of a block being mined - no node, no polling, no missed blocks.

  **What's new:**

  - **Bitcoin mainnet support** on the same Streams developer model used for EVM and Solana
  - **Dual-phase notifications** - matched transactions fire a webhook in the mempool (unconfirmed) and again on block confirmation, so you can mark deposits `pending` then `confirmed` from the same stream
  - **All address formats supported** - P2PKH (legacy `1...`), P2SH (SegWit-wrapped `3...`), and Bech32 native SegWit (`bc1q...`)
  - **Xpub support** - attach an extended public key and Moralis derives and monitors its addresses automatically, ideal for HD wallets
  - **Automatic retries** until your endpoint returns HTTP 200

  **Monitoring modes available at launch:**

  - `addresses` — watch specific Bitcoin addresses
  - `xpub` — derive and monitor addresses from an extended public key
  - `allAddresses` — firehose mode: receive every Bitcoin transaction

  **Use cases:** exchange deposit detection (mempool → confirmed lifecycle), cold wallet surveillance, mining pool payout tracking, and real-time treasury monitoring for corporate or DAO-held BTC.

  A few Bitcoin-specific behaviors to plan around: input `address` and `value` fields are not populated (inbound detection only), output values are BTC decimals rather than satoshis, and `isCoinbase` should be detected via heuristic. See the [Bitcoin Streams docs](/streams/bitcoin-streams) for the full payload structure and processing patterns.
