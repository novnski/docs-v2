Moralis **Data Feeds** give you the complete, decoded onchain dataset, including every DEX trade, as a real-time
stream you own. This guide moves your `/wallets/:address/swaps` integration onto Data Feeds, so a wallet's trade
history, with the bought and sold legs and their USD values, comes straight from that data lake, with **no
per-call limits**.

```
GET /wallets/:address/swaps
```

This is a clean migration: a **purpose-built feed** lands every trade by trader, so a wallet's swaps come through
directly. The onchain details are exact; the USD values are computed from the same trades.

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however fits
your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**), **land it
with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery, Spark, DuckDB,
dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

For a wallet's trade history, the **sink** is the smoothest path, so we'll use it here. Because trades are events,
[streaming](#other-ways-to-consume-this-data) fits live trade monitoring.

## What to expect

You're moving from a single pre-packaged response to the **trades that produce it**, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model.

**Comes through exactly**
- **The trade** (`transactionHash`, `transactionType` buy/sell, `blockNumber`, `blockTimestamp`), the **pair** and
  **exchange** (`pairAddress`, `exchangeName`), and the **bought / sold legs** (token address, amount, symbol),
  straight from the chain.

**Calculated for you, from real trades**
- **USD values** (`usdPrice`, `usdAmount`, `totalValueUsd`, `baseQuotePrice`) come from live onchain prices, very
  close, compare with a small tolerance.

**Add the extras you want**
- `walletAddressLabel`, `entity`, `entityLogo`, `exchangeLogo`, and the per-token logos are off-chain, bring your
  own lists or drop them. `subCategory` (accumulation / distribution) is a classification, define your own rule.

**Good to know**
- The feed lands both direct pool fills and aggregator-routed trades; a `source_kind` distinguishes them.

## Before you begin

- A running Data Feeds **sink** writing to a database, see the [quickstart](/data-feeds/migration/quickstart).
- The recipe below applied to that database.
- Your `MORALIS_API_KEY` and the chain you're indexing.

<Note>
**Backfill is your choice here.** Swaps are an *event list*, so you decide how much history to index. Run the
recipe `realtime` for a live feed, or backfill `historical` / `hybrid` for a wallet's complete trade history. See
[History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipe

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| Every DEX trade by wallet | `swapsByWallet` | `swaps` |
| Token names / symbols | `tokenMetadata` | `token_metadata` |

`swapsByWallet` indexes the trades on `trader_address`, so a by-wallet lookup is fast. It lands both direct pool
fills and aggregator trades, USD-enriched in-block.

### Step 2: Query a wallet's swaps

```ts
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function getWalletSwaps(wallet: string, limit = 100, before?: number) {
  const { rows } = await pool.query(
    `SELECT s.*
     FROM swaps s
     WHERE s.trader_address = $1
       AND ($2::bigint IS NULL OR s.block_number < $2)   -- keyset pagination
     ORDER BY s.block_number DESC
     LIMIT $3`,
    [wallet.toLowerCase(), before ?? null, limit],
  );
  return rows;   // each row carries the side, pool, legs, price_usd, notional_usd
}
```

Join `tokenMetadata` for the leg symbols and derive `pairLabel` from them. Filter by `side` for the legacy
`transactionTypes` (buy/sell). That's it, you're serving a wallet's trade history from a dataset you own.

### Step 3: Add the extras you want

`walletAddressLabel`, `entity`, `entityLogo`, `exchangeLogo`, and the token logos are off-chain, bring your own
directory or drop them. For `subCategory` (accumulation / distribution), apply your own classification over the
wallet's trades.

## Other ways to consume this data

- **Your existing message clients.** A **Kafka / AMQP / SQS** consumer on the swaps reacts to a wallet's trades as
  they land, live trade monitoring without polling.
- **REST / Arrow Flight.** Read the decoded block stream directly (`GET /api/v1/continuum/{namespace}/{topic}`),
  ETH namespace `0x1`, topic `master-4`.
- **Your warehouse / notebook.** Every feed is an Iceberg table, query trades from **Snowflake, BigQuery, Spark,
  DuckDB, dbt** without moving data.

See the **Data Feeds API reference** and **protocol guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg).

## Field mapping reference

The **Fidelity** column shows how each value compares to the old endpoint: **exact** (from the chain),
**calculated** (from real trades), or **add yourself** (off-chain).

| `/wallets/:address/swaps` | Data Feeds | Fidelity |
|---|---|---|
| `transactionHash`, `transactionIndex`, `blockNumber`, `blockTimestamp` | `swaps.*` | exact |
| `transactionType` (buy/sell) | `swaps.side` | exact |
| `pairAddress`, `exchangeName` | `swaps.pool_address` / `protocol` | exact |
| `baseToken`, `quoteToken`, `bought`/`sold` (address, amount) | `swaps` token legs | exact |
| `bought/sold.symbol`, `name`, `pairLabel` | `tokenMetadata` / derive | exact |
| `usdPrice`, `usdAmount`, `totalValueUsd`, `baseQuotePrice` | `swaps.price_usd` / `notional_usd` | calculated |
| `walletAddressLabel`, `entity`, `entityLogo`, `exchangeLogo`, token logos | add yourself | off-chain |
| `subCategory` | classify yourself | off-chain |

## Good to know

- **A purpose-built feed mirrors this endpoint**, `swapsByWallet`, indexed by trader.
- **USD values are calculated** from real trades, compare with a tolerance.
- **Both pool fills and aggregator trades** are landed; `source_kind` distinguishes them.
- **Filters are just SQL** (date/block windows, `side` for buy/sell).
- **Freshness.** ClickHouse is recommended for real-time; Postgres and MySQL carry the flat `swaps` table.
