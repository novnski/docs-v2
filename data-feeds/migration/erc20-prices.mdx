Moralis **Data Feeds** give you the complete, decoded onchain dataset, including a live USD and native mark for
every token, computed from real DEX trades. This guide moves your `/erc20/prices` batch integration onto Data
Feeds, so you price tokens straight from that data lake, with **no per-call limits**, **no 100-token batch cap**,
and full control over how you store, serve, and query prices.

```
POST /erc20/prices
```

This is one of the most natural migrations in the set: the old endpoint's price is **already DEX-derived** (it
even tells you the exchange and pair it came from), and Data Feeds computes its marks from those **same trades**.
So the price, the pair it came from, and the 24-hour change all map straight across.

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however fits
your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**), **land it
with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery, Spark, DuckDB,
dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

For pricing a set of tokens on demand, the **sink** is the smoothest path, so we'll use it here. Because prices
are events, [streaming](#other-ways-to-consume-this-data) is also a great fit if you want a live ticker.

## What to expect

You're moving from a single pre-packaged response to the **underlying data that produces it**, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model. Here's how it
applies to token prices:

**Comes through exactly**
- **The price source** (`pairAddress`, `exchangeName`/`protocol`) and **when it last changed**
  (`priceLastChangedAtBlock`, `blockTimestamp`), straight from the chain.
- **Token details** (`name`, `symbol`, `decimals`), from the token contract.

**Calculated for you, from real trades**
- **Prices** (`usdPrice`, `nativePrice`) come from live onchain DEX activity, the same trades the old endpoint
  used. They track it closely; because you're computing the mark yourself from those trades, compare with a small
  tolerance rather than expecting an identical figure.
- **24-hour change** (`24hrPercentChange`, `usdPrice24hr`, `usdPrice24hrUsdChange`) is a quick lookup of the
  price ~24 hours ago against the latest, you derive it from the same price history.
- **Pair liquidity** (`pairTotalLiquidityUsd`) comes from the pair's reserves priced in USD, add a pair recipe if
  you need it (or omit it).

**Yours to control**
- **Which pair sets "the price."** When a token trades on several pairs, the old endpoint picked one (typically
  the deepest-liquidity pair). Data Feeds gives you **every pair's mark**, so you choose the rule, newest overall,
  or newest from the deepest pair, and your "the price" is well-defined and consistent.

**Add the extras you want**
- `tokenLogo`, `possibleSpam`, `verifiedContract`, and `securityScore` are off-chain signals layered on top of
  the chain, so they're not in the feed. Drop them, bring your own lists, or layer in a token list, see
  [step 4](#step-4-add-the-extras-you-want).

**Good to know**
- A token's mark comes from DEX activity, so a token that hasn't traded recently may carry a slightly older mark
  (on ClickHouse the recipe keeps the freshest mark per token for exactly this carry-forward case).

## Before you begin

- A running Data Feeds **sink** writing to a database, see the [quickstart](/data-feeds/migration/quickstart). ClickHouse is
  recommended here for real-time pricing and the latest-mark lookup.
- The recipes below applied to that database.
- Your `MORALIS_API_KEY` and the chain you're pricing on.

<Note>
**Backfill is your choice here.** Prices are an *event list*, not current state, so you decide how much history to
index. For "what's the price of these tokens **now**", you only need the feed running recently (the latest mark
per token is enough). Only index further back if you want historical prices (the old `to_block` behavior) or a
longer 24-hour/sparkline window. See [History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipes

A token's price draws on two parts of the dataset, plus an optional third for pair liquidity:

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| USD / native price + the pair it came from | `tokenPriceHistory` | `token_price_updates` |
| Token details (name, symbol, decimals) | `tokenMetadata` | `token_metadata` |
| Pair liquidity (`pairTotalLiquidityUsd`), optional | the `pairReserves` recipe | the pair's reserves |

Point the recipes at the same database and start them. `tokenPriceHistory` lands one row per price update per
`(token, pair, protocol)`, which is exactly the DEX-derived mark the old endpoint reported.

### Step 2: Bring it together in one view

Take the **newest mark per token** and join in the token details. Here's a Postgres example to adapt to your
sink (the price columns are calculated, as noted in [What to expect](#what-to-expect)):

```sql
CREATE VIEW token_prices AS
WITH latest AS (
  SELECT DISTINCT ON (token_address)
         token_address, usd_price, native_price, pair_address, protocol,
         block_number, block_timestamp
  FROM   token_price_updates
  ORDER  BY token_address, block_number DESC          -- newest mark per token
),
prior AS (                                             -- mark ~24h earlier, for the change fields
  SELECT DISTINCT ON (token_address) token_address, usd_price AS usd_price_24h
  FROM   token_price_updates
  WHERE  block_timestamp <= extract(epoch FROM now()) - 86400
  ORDER  BY token_address, block_number DESC
)
SELECT
  l.token_address,
  m.symbol, m.name, m.decimals,
  l.usd_price,
  l.native_price,
  l.pair_address,
  l.protocol                                   AS exchange_name,
  l.block_number                               AS price_last_changed_at_block,
  l.block_timestamp,
  p.usd_price_24h,
  l.usd_price - p.usd_price_24h                AS usd_price_24hr_usd_change,
  (l.usd_price - p.usd_price_24h)
    / NULLIF(p.usd_price_24h, 0) * 100         AS usd_price_24hr_percent_change
FROM latest l
LEFT JOIN token_metadata m ON m.token_address = l.token_address
LEFT JOIN prior          p ON p.token_address = l.token_address;
```

Trades on more than one pair? Pick your reference pair in the `latest` CTE (for example, order by a liquidity
column from your pair recipe before `block_number`) so "the price" is the one you intend.

### Step 3: Query it from your app

Price any number of tokens in one query, no 100-token cap:

```ts
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function getTokenPrices(tokenAddresses: string[]) {
  const { rows } = await pool.query(
    `SELECT * FROM token_prices WHERE token_address = ANY($1)`,
    [tokenAddresses.map((t) => t.toLowerCase())],
  );
  return rows;
}
```

That's it, you're pricing tokens from a dataset you own, in real time, from the same DEX trades the old endpoint
used, with no batch cap and the freedom to query it any way you like.

### Step 4: Add the extras you want

`tokenLogo`, `possibleSpam`, `verifiedContract`, and `securityScore` are off-chain signals, so they're not part
of the onchain dataset. When you want them, you've got options:

- **Skip them** if your app doesn't use them.
- **Bring your own source**, a public token list for logos, or your own allow/deny lists for spam and
  verification.
- **Layer them in** from a dedicated metadata source alongside your Data Feeds tables.

## Other ways to consume this data

The sink is the smoothest path for on-demand pricing, but the **same feed** is available however you prefer to
build, all reading the one data lake:

- **Your existing message clients.** Point a **Kafka**, **AMQP / RabbitMQ**, or **Amazon SQS** consumer at Data
  Feeds and react to price updates as they land, perfect for a live price ticker without polling.
- **REST / Arrow Flight.** Read the decoded block stream directly, for Ethereum, namespace `0x1`, topic
  `master-4`:
  ```
  GET /api/v1/continuum/{namespace}/{topic}            # records by position range
  GET /api/v1/continuum/{namespace}/{topic}/schema     # the topic's Arrow schema
  ```
  Each record is a block carrying the decoded `tokenPriceUpdates` array the recipe projects from. Arrow Flight
  (gRPC) is the high-throughput option for large pulls.
- **Your warehouse / notebook.** Every feed is an Iceberg table, query price history straight from **Snowflake,
  BigQuery, Spark, Trino, Databricks, DuckDB, Pandas, or dbt** without moving data.

See the **Data Feeds API reference** and **protocol guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg) for
connection details.

## Field mapping reference

The **Fidelity** column shows how each value compares to the old endpoint: **exact** (from the chain),
**calculated** (from real trades, very close), or **add yourself** (off-chain signal).

| `/erc20/prices` | Data Feeds | Fidelity |
|---|---|---|
| `tokenAddress` | `token_price_updates.token_address` | exact |
| `usdPrice` / `usdPriceFormatted` | latest `token_price_updates.usd_price` | calculated |
| `nativePrice` | latest `token_price_updates.native_price` | calculated |
| `pairAddress` | `token_price_updates.pair_address` | exact |
| `exchangeName` | `token_price_updates.protocol` | exact |
| `exchangeAddress` | `pairAddressLookup.factory_address` (compose via the pair) | exact |
| `priceLastChangedAtBlock` | `token_price_updates.block_number` | exact |
| `blockTimestamp` | `token_price_updates.block_timestamp` | exact |
| `tokenName`, `tokenSymbol`, `tokenDecimals` | `token_metadata.*` | exact |
| `24hrPercentChange` / `usdPrice24hr*` | derive from price history | calculated |
| `pairTotalLiquidityUsd` | pair recipe (reserves x price) | calculated |
| `tokenLogo` | add yourself | off-chain |
| `possibleSpam`, `verifiedContract`, `securityScore` | add yourself | off-chain |

## Good to know

- **Same source as the old endpoint.** Both price from onchain DEX trades, so the marks line up closely, best
  compared with a small tolerance.
- **You choose the reference pair.** A token can trade on many pairs; you decide which mark is "the price", giving
  you a stable, well-defined figure.
- **No batch cap.** The old endpoint takes up to 100 tokens per call; querying your own table has no such limit.
- **Coverage follows DEX activity.** A token that hasn't traded recently may have an older mark, the ClickHouse
  recipe keeps the freshest mark per token to carry it forward.
- **Units.** `native_price` is a scalar (the old `nativePrice` was an object), and `block_timestamp` is in
  seconds (the old `blockTimestamp` was milliseconds), small shape adjustments when you map.
- **Freshness.** ClickHouse is recommended for real-time pricing and the latest-mark lookup; Postgres and MySQL
  carry the flat table (with the realtime reorg caveat, see the recipe README).
