Moralis **Data Feeds** give you the complete, decoded onchain dataset, including every transaction and every log,
as a real-time stream you own. This guide moves your `/transaction/:hash/verbose` integration onto Data Feeds, so
a transaction's raw fields and its logs come straight from that data lake, with **no per-call limits** and full
control over how you store, query, and decode them.

```
GET /transaction/:transaction_hash/verbose
```

<Note>
**What's exact vs what you decode.** Data Feeds delivers the **raw transaction and its logs exactly**. The part
that makes this endpoint "verbose", the **ABI-decoded function call and events**, is a decode step: the feed
carries raw `input`, topics, and log `data`, and you decode them from the contract ABI. The good news: for
**standard events** (ERC-20/721 transfers, swaps, and more) Data Feeds **already decodes them into typed feeds**,
so you rarely decode raw logs by hand. See [The `block` array](/data-feeds/concepts/the-block-array) for how raw transactions
and logs are laid out.
</Note>

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however fits
your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**), **land it
with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery, Spark, DuckDB,
dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

A Data Feed delivers **one row per block**, with the raw header, transactions, and logs in a flattened `block`
array, plus typed arrays for decoded events. For a transaction lookup, the **sink** lands the logs in a queryable
table, so we'll use it here.

## What to expect

You're moving from a single pre-packaged response to the **underlying data that produces it**, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model. For a transaction:

**Comes through exactly**
- **The transaction** (`from_address`, `to_address`, `value`, `input`, `nonce`, gas and receipt fields) and its
  **block context**, straight from the chain.
- **The logs** (emitter `address`, `topic0`..`topic3`, raw `data`, `log_index`), one row per event.
- **Internal transactions**, the trace-derived value transfers, where available.

**Decoded for you (standard events)**
- ERC-20/721 transfers, swaps, and other common events arrive **already decoded** in typed feeds
  (`tokenTransfers`, `tokenSwaps`, `nftTokenTransfers`, ...), so the `decoded_event` for those is a typed row, not
  a hand-decode.

**Yours to decode (custom contracts)**
- For events and the function call (`decoded_call`) that aren't standard, decode the raw `input` and log
  topics/`data` with the contract's ABI, a small step with `ethers`/`viem` once you have the ABI.

**Calculated for you**
- `transaction_fee` is `receipt_gas_used x gas_price`.

**Add the extras you want**
- `from/to_address_entity`, `*_label`, and `*_entity_logo` are off-chain address labels, bring your own directory
  or drop them.

## Before you begin

- A running Data Feeds **sink** writing to a database, see the [quickstart](/data-feeds/migration/quickstart).
- The recipe below applied to that database, plus access to the Data Feeds API for the raw transaction row.
- The **ABI** of any custom contracts whose calls/events you need to decode.
- Your `MORALIS_API_KEY` and the chain you're indexing.

<Note>
**Index the history you'll look up.** A by-hash lookup is a point read into block history, so the block containing
the transaction must be indexed. If you look up **arbitrary historical** transactions, backfill `historical` or
`hybrid` across the range you need (full history for any hash); if you only look up **recent** transactions, a
recent window is enough. See [History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipe

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| Every log, queryable by transaction | `logsByContract` | `contract_logs` |

`contract_logs` carries `tx_hash`, `transaction_index`, `log_index`, the emitter `contract_address`,
`topic0`..`topic3`, and the raw `data`, exactly the raw side of each `logs[]` entry. (Index `tx_hash` for the
by-hash lookup.) For the transaction's own fields (`from`, `to`, `value`, `input`, gas, receipt), read the raw
`transaction` row from the `block` array via the Data Feeds API, you have its block number from the matching
`contract_logs` rows.

### Step 2: Fetch a transaction's logs by hash

```ts
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function getTransactionLogs(txHash: string) {
  const { rows } = await pool.query(
    `SELECT block_number, log_index, contract_address,
            topic0, topic1, topic2, topic3, data
     FROM contract_logs
     WHERE tx_hash = $1
     ORDER BY log_index`,
    [txHash.toLowerCase()],
  );
  return rows;   // raw logs; block_number tells you which block to read for the tx row
}
```

Read the matching `transaction` row (raw `from`/`to`/`value`/`input`/gas/receipt) from that block via the Data
Feeds API, and derive `transaction_fee = receipt_gas_used x gas_price`.

### Step 3: Decode the call and events

- **Standard events** are already decoded, join the typed feeds (`tokenTransfers`, `tokenSwaps`,
  `nftTokenTransfers`, ...) for this transaction instead of decoding raw logs.
- **Custom events and the function call** decode from the contract ABI. With the ABI in hand it's a few lines:

  ```ts
  import { Interface } from 'ethers';

  const iface = new Interface(contractAbi);
  const decodedCall = iface.parseTransaction({ data: tx.input, value: tx.value });
  const decodedEvent = iface.parseLog({ topics: [log.topic0, log.topic1, log.topic2, log.topic3].filter(Boolean), data: log.data });
  ```

That's it, you're serving a transaction's raw fields and logs from a dataset you own, with standard events decoded
for free and the custom bits decoded on your terms.

## Other ways to consume this data

The sink is one way in, but the **same feed** is available however you prefer to build, all reading the one data
lake:

- **Your existing message clients.** Point a **Kafka**, **AMQP / RabbitMQ**, or **Amazon SQS** consumer at the
  feed to watch transactions and logs as they land, ideal for monitoring every transaction touching a contract.
- **REST / Arrow Flight.** Read the decoded block stream directly, for Ethereum, namespace `0x1`, topic
  `master-4`:
  ```
  GET /api/v1/continuum/{namespace}/{topic}            # records by position range
  GET /api/v1/continuum/{namespace}/{topic}/schema     # the topic's Arrow schema
  ```
  Each record is a block carrying the raw `block` array (transaction and log rows) and the typed event arrays.
  Arrow Flight (gRPC) is the high-throughput option for large pulls.
- **Your warehouse / notebook.** Every feed is an Iceberg table, query transactions and logs straight from
  **Snowflake, BigQuery, Spark, Trino, Databricks, DuckDB, Pandas, or dbt** without moving data.

See the **Data Feeds API reference**, the [block array concept](/data-feeds/concepts/the-block-array), and the **protocol
guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg) for connection details.

## Field mapping reference

The **Fidelity** column shows how each value compares to the old endpoint: **exact** (from the chain),
**decoded** (standard events, decoded for you, or custom, decoded from the ABI), or **add yourself** (off-chain).

| `/transaction/:hash/verbose` | Data Feeds | Fidelity |
|---|---|---|
| `hash`, `nonce`, `transaction_index` | `block` array transaction row | exact |
| `from_address`, `to_address`, `value`, `input` | `block` array transaction row | exact |
| `gas`, `gas_price`, `receipt_*` | `block` array transaction row | exact |
| `transaction_fee` | derive: `receipt_gas_used x gas_price` | exact |
| `block_number`, `block_timestamp`, `block_hash` | block / transaction row | exact |
| `logs[]` (address, topics, data, indices) | `contract_logs` (`logsByContract`) | exact |
| `logs[].decoded_event` (standard) | typed feeds (`tokenTransfers`, `tokenSwaps`, ...) | decoded |
| `logs[].decoded_event` (custom) | decode topics + data with the ABI | decoded |
| `decoded_call` | decode `input` with the ABI | decoded |
| `internal_transactions` | not delivered by a shipped recipe today (`internalTransactions` exists upstream but is not yet exposed; it is not carried in the `block` array) | gap |
| `from/to_address_entity`, `*_label`, `*_entity_logo` | add yourself | off-chain |

## Good to know

- **Raw is exact, decode is yours.** The transaction and logs come through exactly; the ABI decoding is a step you
  own, made easy by the typed feeds for standard events.
- **Logs join on `transactionIndex` in the raw block array** (a raw log row has no tx hash); the `logsByContract`
  recipe already attaches `tx_hash` for you.
- **By-hash is a point lookup.** Data Feeds is organized by block, index `tx_hash` on `contract_logs` (or keep
  your own hash to block map) to fetch by hash.
- **Just need an occasional decoded transaction?** An RPC node or the hosted API is a simpler fit for that one
  narrow job; Data Feeds is about owning and streaming the raw transaction and log data at scale.
- **Freshness.** Run the recipe `realtime` for a live feed; ClickHouse is recommended for real-time and hybrid
  modes (see the recipe README).
