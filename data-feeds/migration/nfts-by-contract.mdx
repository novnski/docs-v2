Moralis **Data Feeds** give you the complete, decoded onchain dataset, including every NFT and its owner, as a
real-time stream you own. This guide moves your `/nft/:address` integration onto Data Feeds, so a collection's
NFTs, with their current owners and mint provenance, come straight from that data lake, with **no per-call
limits**.

```
GET /nft/:address
```

This is the **collection-listing** version of [NFT metadata (batch)](/data-feeds/migration/nft-multiple): the same
recipes and the same split, the onchain layer (ownership, mint, identity) is exact, and the resolved
metadata/media/rarity/floor is the off-chain layer you bring.

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however fits
your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**), **land it
with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery, Spark, DuckDB,
dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

For listing a collection's NFTs, the **sink** lands ownership in a queryable table, so we'll use it here.

## What to expect

You're moving from a single pre-packaged response to the **underlying data that produces it**, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model.

**Comes through exactly (from Data Feeds)**
- **Every token_id** in the collection and its **current owner** (`owner_of`, `amount`), **mint provenance**
  (`block_number_minted`, `minter_address`), `contract_type`, and the collection `name` / `symbol`.

**Bring your metadata layer (off-chain)**
- `token_uri`, `metadata`, `media`, `rarity_*`, `floor_price*`, `list_price`, `possible_spam`,
  `verified_collection`, and the collection editorial fields are resolved off-chain, pair Data Feeds with a
  metadata resolver and your rarity / floor sources (see [NFT metadata](/data-feeds/migration/nft-multiple)).

**Good to know**
- For ERC-1155, a token_id can have many owners, you get a row per `(token_id, owner)`.

## Before you begin

- A running Data Feeds **sink** writing to a database, see the [quickstart](/data-feeds/migration/quickstart).
- The recipes below applied to that database.
- A metadata-resolution path for the off-chain fields you need.
- Your `MORALIS_API_KEY` and the chain you're indexing.

<Note>
**Plan for full history, from the collection's first block.** To list every token_id and its current owner, the
`nftOwnersByContract` recipe must backfill the collection's **full history from its deployment block** (run
`historical` / `hybrid`). Because this is by-collection, you only need history since it deployed. See
[History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipes

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| Every token_id + current owner | `nftOwnersByContract` | `nft_owners` |
| Collection name / symbol | `nftCollectionMetadata` | `nft_collection_metadata` |
| Mint provenance | `nftTransfers` | the transfer log (mint = from the zero address) |
| Realized sale history | `nftTrades` | marketplace trades per token |

### Step 2: List the collection's NFTs

```sql
SELECT o.token_id, o.wallet_address AS owner_of, o.amount, o.contract_type,
       c.name, c.symbol, o.block_number
FROM nft_owners o
LEFT JOIN nft_collection_metadata c ON c.token_address = o.token_address
WHERE o.token_address = $1 AND o.amount > 0
ORDER BY o.token_id;
```

Join `nftTransfers` (first transfer, from the zero address) for `block_number_minted` / `minter_address`, and
`nftTrades` for sale history.

### Step 3: Bring your metadata layer

Resolve each token's `tokenURI` and fetch / normalize the JSON and media, and pull rarity and floor from your own
sources, keyed by `(token_address, token_id)`. See [NFT metadata](/data-feeds/migration/nft-multiple) for the
resolver pattern. If you already run a metadata indexer, keep it for this part; Data Feeds gives you the ownership
and provenance to pair with it.

## Other ways to consume this data

- **Your existing message clients.** A **Kafka / AMQP / SQS** consumer on the NFT transfers keeps ownership live.
- **REST / Arrow Flight.** Read the decoded block stream directly (`GET /api/v1/continuum/{namespace}/{topic}`),
  ETH namespace `0x1`, topic `master-4`.
- **Your warehouse / notebook.** Every feed is an Iceberg table, query ownership from **Snowflake, BigQuery,
  Spark, DuckDB, dbt** without moving data.

See the **Data Feeds API reference** and **protocol guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg).

## Field mapping reference

The **Fidelity** column shows how each value compares to the old endpoint: **exact** (from the chain),
**calculated** (sale USD), or **add yourself** (off-chain metadata layer).

| `/nft/:address` | Data Feeds | Fidelity |
|---|---|---|
| `token_address`, `token_id`, `contract_type`, `owner_of`, `amount` | `nft_owners.*` | exact |
| `block_number`, `block_number_minted`, `minter_address` | `nft_owners` / `nftTransfers` | exact |
| `name`, `symbol` | `nft_collection_metadata.*` | exact |
| `token_hash` | derive | exact |
| `last_sale` USD | `nftTrades` + price feed | calculated |
| `token_uri`, `metadata`, `media`, `rarity_*`, `floor_price*`, `list_price`, `possible_spam`, `verified_collection`, collection editorial, `*_sync` | add yourself | off-chain |

## Good to know

- **Collection listing of [NFT metadata](/data-feeds/migration/nft-multiple)**, same onchain-exact + bring-metadata split.
- **ERC-1155** gives a row per `(token_id, owner)`.
- **Big collections** paginate heavily, keyset on `token_id` (the legacy `totalRanges` / `range` is parallel scan).
- **Backfill from the collection's deploy block.**
