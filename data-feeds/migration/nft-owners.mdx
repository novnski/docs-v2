Moralis **Data Feeds** give you the complete, decoded onchain dataset, including who owns every NFT, as a
real-time stream you own. This guide moves your `/nft/:address/owners` integration onto Data Feeds, so a
collection's holdings, every `(token_id, owner)`, come straight from that data lake, with **no per-call limits**.

```
GET /nft/:address/owners
```

This is the **holdings view** of [NFTs by contract](/data-feeds/migration/nfts-by-contract), the same recipe and
the same split: ownership is exact from a purpose-built feed, and the resolved metadata is the off-chain layer you
bring.

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however fits
your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**), **land it
with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery, Spark, DuckDB,
dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

For a collection's owner list, the **sink** lands ownership in a queryable table, so we'll use it here.

## What to expect

You're moving from a single pre-packaged response to the **underlying data that produces it**, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model.

**Comes through exactly (from Data Feeds)**
- **Every holding** (`owner_of`, `token_id`, `amount`), with **mint provenance** (`block_number_minted`,
  `minter_address`), `contract_type`, and the collection `name` / `symbol`.

**Bring your metadata layer (off-chain)**
- `token_uri`, `metadata`, `rarity_*`, `floor_price*`, `list_price`, `possible_spam`, `verified_collection`, and
  the sync timestamps are resolved off-chain, pair Data Feeds with a metadata resolver (see
  [NFT metadata](/data-feeds/migration/nft-multiple)).

**Good to know**
- ERC-721 has one owner per token_id (same as [NFTs by contract](/data-feeds/migration/nfts-by-contract)); ERC-1155
  can have many, you get a row per `(token_id, owner)`.

## Before you begin

- A running Data Feeds **sink** writing to a database, see **Run a recipe** (quickstart).
- The recipes below applied to that database.
- Your `MORALIS_API_KEY` and the chain you're indexing.

<Note>
**Plan for full history, from the collection's first block.** To list every current owner, the
`nftOwnersByContract` recipe must backfill the collection's **full history from its deployment block**. Because
this is by-collection, you only need history since it deployed. See
[History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipes

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| Every current holding (token_id + owner) | `nftOwnersByContract` | `nft_owners` |
| Collection name / symbol | `nftCollectionMetadata` | `nft_collection_metadata` |
| Mint provenance | `nftTransfers` | the transfer log (mint = from the zero address) |

`nftOwnersByContract` answers "every current owner of collection X" directly, that's this endpoint.

### Step 2: List the owners

```sql
SELECT o.token_id, o.wallet_address AS owner_of, o.amount, o.contract_type,
       c.name, c.symbol, o.block_number
FROM nft_owners o
LEFT JOIN nft_collection_metadata c ON c.token_address = o.token_address
WHERE o.token_address = $1 AND o.amount > 0
ORDER BY o.token_id, o.wallet_address;
```

Join `nftTransfers` for `block_number_minted` / `minter_address`. For the resolved metadata, rarity, and floor,
bring your metadata layer (see [NFT metadata](/data-feeds/migration/nft-multiple)).

## Other ways to consume this data

- **Your existing message clients.** A **Kafka / AMQP / SQS** consumer on the NFT transfers keeps ownership live.
- **REST / Arrow Flight.** Read the decoded block stream directly (`GET /api/v1/continuum/{namespace}/{topic}`),
  ETH namespace `0x1`, topic `master-4`.
- **Your warehouse / notebook.** Every feed is an Iceberg table, query ownership from **Snowflake, BigQuery,
  Spark, DuckDB, dbt** without moving data.

See the **Data Feeds API reference** and **protocol guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg).

## Field mapping reference

| `/nft/:address/owners` | Data Feeds | Fidelity |
|---|---|---|
| `token_id`, `token_address`, `contract_type`, `owner_of`, `amount` | `nft_owners.*` | exact |
| `block_number`, `block_number_minted`, `minter_address` | `nft_owners` / `nftTransfers` | exact |
| `name`, `symbol` | `nft_collection_metadata.*` | exact |
| `token_hash` | derive | exact |
| `last_sale` USD | `nftTrades` + price feed | calculated |
| `token_uri`, `metadata`, `rarity_*`, `floor_price*`, `list_price`, `possible_spam`, `verified_collection`, `*_sync` | add yourself | off-chain |

## Good to know

- **Holdings view of [NFTs by contract](/data-feeds/migration/nfts-by-contract)**, same onchain-exact +
  bring-metadata split.
- **ERC-1155** gives a row per `(token_id, owner)`; **ERC-721** one owner per id.
- **Big collections** paginate heavily, keyset on `(token_id, wallet_address)`.
- **Backfill from the collection's deploy block.**
