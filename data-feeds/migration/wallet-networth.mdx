Moralis **Data Feeds** give you the complete, decoded onchain dataset, every balance and every price, so you can
compute a wallet's net worth yourself, from data you own. This guide moves your `/wallets/:address/net-worth`
integration onto Data Feeds, so the total comes straight from that data lake, in real time, with **no per-call
limits** and full control over which tokens count.

```
GET /wallets/:address/net-worth
```

Net worth is a **roll-up of the wallet's balances and prices**: `SUM(token balance x price) + native balance x
native price`, per chain. If you've already built
[Wallet token balances & prices](/data-feeds/migration/wallet-tokens), this is a `SUM` on top of that.

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however fits
your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**), **land it
with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery, Spark, DuckDB,
dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

For a computed total like net worth, the **sink** is the smoothest path, land balances and prices, then aggregate.

## What to expect

You're moving from a single pre-packaged number to the **data that produces it**, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model. Net worth is a
computed figure, so plan for it as one:

**Calculated for you, from real trades**
- **Net worth is a USD total** built from balances (exact, from the chain) times prices (from live onchain DEX
  trades). It tracks the old endpoint closely; because the prices come from real trades, compare with a small
  tolerance rather than expecting an identical figure.

**Yours to control (this is the whole game)**
- **Which tokens count.** A net-worth number is only as meaningful as the token set behind it. A single spam or
  bogus-priced token can dominate the total, so apply your own spam, dust, and liquidity rules to decide what
  counts. The old `exclude_spam` / `exclude_unverified_contracts` / liquidity filters become your own `WHERE`, and
  here they're essential, not optional polish.

**Good to know**
- Prices come from DEX activity, so a token that hasn't traded recently may have no fresh mark, decide whether to
  value it at zero, carry forward the last mark, or exclude it (each choice moves the total).
- Net worth is often **cross-chain**: each chain is its own feed, compute the total per chain and sum.

## Before you begin

- A running Data Feeds **sink** writing to a Postgres (or MySQL) database, see **Run a recipe** (quickstart).
- The four balance/price recipes from [Wallet token balances & prices](/data-feeds/migration/wallet-tokens) applied
  to that database.
- Your `MORALIS_API_KEY` and the chain(s) you're indexing.

<Note>
**Plan for full history.** A wallet's balances are *current state*, the cumulative result of every transfer, so to
total a *complete* net worth the balance recipes must backfill the **full history** of each chain (run them
`historical` or `hybrid` from an early block). A missed holding silently changes the total. Prices only need as
far back as you want price history. See [History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipes

Net worth draws on the same four recipes as wallet balances and prices:

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| ERC-20 balances per wallet | `tokenBalancesByWalletAddress` | `token_balances` |
| Native (e.g. ETH) balance | `nativeBalances` | `native_balances` |
| Token decimals (to format) | `tokenMetadata` | `token_metadata` |
| Live USD price (token + native) | `tokenPriceHistory` | `token_price_updates` |

These are the recipes behind [Wallet token balances & prices](/data-feeds/migration/wallet-tokens); build that view
first, then aggregate it here.

### Step 2: Sum it into a net worth

Aggregate the per-token USD values from the wallet balances view, and add the native value:

```sql
CREATE VIEW wallet_net_worth AS
WITH tokens AS (
  SELECT wallet_address,
         sum(usd_value) AS token_balance_usd        -- exclude what shouldn't count (see step 3)
  FROM   wallet_token_balances_price                -- the view from guide #1
  WHERE  usd_value IS NOT NULL
  GROUP  BY wallet_address
),
native AS (
  SELECT n.wallet_address,
         n.balance / 1e18                       AS native_balance_formatted,
         n.balance / 1e18 * p.usd_price         AS native_balance_usd
  FROM   native_balances n
  LEFT JOIN LATERAL (
    SELECT usd_price FROM token_price_updates
    WHERE token_address = lower('0xC02aaa39b223FE8D0A0e5C4F27eAD9083C756Cc2')  -- WETH = native mark
    ORDER BY block_number DESC LIMIT 1
  ) p ON true
)
SELECT
  coalesce(t.wallet_address, n.wallet_address)            AS wallet_address,
  n.native_balance_formatted,
  n.native_balance_usd,
  coalesce(t.token_balance_usd, 0)                        AS token_balance_usd,
  coalesce(t.token_balance_usd, 0) + coalesce(n.native_balance_usd, 0) AS networth_usd
FROM tokens t
FULL JOIN native n ON n.wallet_address = t.wallet_address;
```

For **cross-chain** net worth, run this per chain (each chain is its own feed) and sum `networth_usd` into a
`total_networth_usd`.

### Step 3: Decide what counts (do not skip)

A net-worth total is dominated by its worst data point, so curate the token set before you trust the number:

- **Spam and unverified:** filter with your own allow/deny list (the old `exclude_spam` /
  `exclude_unverified_contracts`).
- **Dust and illiquid:** require a minimum pair liquidity or a minimum USD value per holding (the old
  `min_pair_side_liquidity_usd`).
- **Stale prices:** drop or cap tokens whose last mark is old, and consider an outlier cap so one bogus price
  can't dominate.

Apply these in the `WHERE` of the `tokens` CTE above. They're the difference between a number you can show a user
and a meaningless one.

## Other ways to consume this data

The sink is the smoothest path for a computed total, but the **same feed** is available however you prefer to
build, all reading the one data lake:

- **Your existing message clients.** Point a **Kafka**, **AMQP / RabbitMQ**, or **Amazon SQS** consumer at
  balances and prices and recompute net worth as they change, a live portfolio value without polling.
- **REST / Arrow Flight.** Read the decoded block stream directly (`GET /api/v1/continuum/{namespace}/{topic}`),
  for Ethereum, namespace `0x1`, topic `master-4`. Arrow Flight (gRPC) is the high-throughput option.
- **Your warehouse / notebook.** Every feed is an Iceberg table, compute net worth straight from **Snowflake,
  BigQuery, Spark, Trino, Databricks, DuckDB, Pandas, or dbt** without moving data.

See the **Data Feeds API reference** and **protocol guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg) for
connection details.

## Field mapping reference

The **Fidelity** column shows how each value compares to the old endpoint: **exact** (from the chain) or
**calculated** (from real trades, very close). Net worth is a USD total, so it's calculated by nature.

| `/wallets/:address/net-worth` | Data Feeds | Fidelity |
|---|---|---|
| `native_balance`, `native_balance_formatted` | `native_balances.balance` | exact |
| `native_balance_usd` | derive: native balance x native price | calculated |
| `token_balance_usd` | `SUM(usd_value)` over the wallet balances view | calculated |
| `networth_usd` | derive: native + token USD | calculated |
| `total_networth_usd` | derive: sum across chains | calculated |

## Good to know

- **Net worth is a roll-up of [Wallet token balances & prices](/data-feeds/migration/wallet-tokens).** Build that
  view, then sum.
- **The token set is the headline.** A single spam or bogus-priced token can dominate the total, curate before you
  trust it.
- **Compare with a tolerance.** USD comes from real DEX trades, very close to the old endpoint, not bit-identical.
- **Cross-chain** totals are per-chain feeds summed.
- **No wallet-size cap.** The old endpoint can struggle on very large wallets; your own dataset has none.
- **Freshness.** Balances are current-state on Postgres or MySQL; ClickHouse is recommended for real-time and
  hybrid modes (and keeps a latest price per token for carry-forward valuation).
