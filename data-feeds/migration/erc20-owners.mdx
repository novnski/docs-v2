Moralis **Data Feeds** give you the complete, decoded onchain dataset, every transfer, balance, and price, as
a real-time stream you own. This guide moves your `/erc20/:token_address/owners` integration onto Data Feeds, so
a token's full holder list, every owner, their balance, and USD value, comes straight from that data lake,
with **no per-call limits** and full control over how you rank, filter, and query it.

```
GET /erc20/:token_address/owners
```

This is one of the most direct migrations: the **`tokenHolders`** recipe is purpose-built to mirror this
endpoint, so the holder list, balances, and USD values come through with very little work on your side.

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however
fits your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**),
**land it with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery,
Spark, DuckDB, dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

For a holder list, the **sink** is the smoothest path, so we'll use it here.
([Other ways to consume it](#other-ways-to-consume-this-data) are below.)

## What to expect

You're moving from one pre-packaged response to the underlying data that produces it, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model. Here's how it
applies to token owners:

**Comes through exactly**
- **The holder list and balances** (`owner_address`, `balance`), straight from the chain. With token decimals
  (one extra recipe), the human-readable `balance_formatted` and `percentage_relative_to_total_supply` too.

**Calculated for you, from real trades**
- **USD value** (`usd_value`) is computed from live onchain DEX prices. It tracks the endpoint closely; compare
  with a small tolerance rather than expecting an exact match, and note a token with no recent trades may value
  at 0.

**Yours to control**
- **Ordering and filtering.** The old endpoint returns biggest-first and only non-zero holders. With your own
  copy you decide, rank by balance or USD value, set your own minimum, or page however you like.

**Add the extras you want**
- `owner_address_label`, `entity`, `entity_logo` (exchange/entity labels) and `is_contract` are off-chain or
  chain-derived signals, so they aren't in the holder data. [Add them yourself](#step-3-add-the-extras-you-want)
  when you need them.

## Before you begin

- A running Data Feeds **sink** writing to a Postgres (or MySQL) database, see the [quickstart](/data-feeds/migration/quickstart).
- The `tokenHolders` recipe applied to that database (add `tokenMetadata` for formatted balances / percentages).
- Your `MORALIS_API_KEY` and the chain you're indexing.

<Note>
**Index from the token's first block.** A holder list is *current state*, the cumulative result of every
transfer of the token, so to return **every** holder you need the token's full transfer history. The good news:
that's just history since the **token launched**, not chain genesis. Backfill `tokenHolders` (`historical` or
`hybrid`) from around the token's deployment block. See [History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipe

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| Holders + balance + USD value, per token | `tokenHolders` | `token_holders` |
| (Optional) decimals + total supply for formatting | `tokenMetadata` | `token_metadata` |

`tokenHolders` keeps one current row per `(token, wallet)` with a non-zero balance, exactly the holder list
this endpoint returns.

### Step 2: Query it from your app

For the core holder list, query `token_holders` directly, and rank biggest-first the way the endpoint did:

```ts
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function getTokenOwners(token: string, limit = 100, offset = 0) {
  const { rows } = await pool.query(
    `SELECT wallet_address AS owner_address,
            balance,
            usd_value
     FROM token_holders
     WHERE token_address = $1
       AND balance > 0               -- current owners only (exclude zeroed-out former holders)
     ORDER BY balance DESC          -- biggest holders first, like the endpoint
     LIMIT $2 OFFSET $3`,
    [token.toLowerCase(), limit, offset],
  );
  return rows;
}
```

Want the human-readable balance and percentage of supply? Join `token_metadata` for `decimals` and
`total_supply`:

```sql
SELECT h.wallet_address AS owner_address,
       h.balance,
       h.balance / power(10, m.decimals)        AS balance_formatted,
       h.usd_value,
       h.balance / NULLIF(m.total_supply, 0)    AS percentage_relative_to_total_supply
FROM token_holders h
LEFT JOIN token_metadata m ON m.token_address = h.token_address
WHERE h.token_address = lower($1)
ORDER BY h.balance DESC
LIMIT $2 OFFSET $3;
```

That's it, you're serving a token's holders, balances, and USD values from a dataset you own, ranked and
filtered however you like, with no per-call limits.

### Step 3: Add the extras you want

`owner_address_label`, `entity`, and `entity_logo` are off-chain labels (which wallets are exchanges, funds,
etc.), and `is_contract` is a chain lookup, none are part of the holder data. When you need them:

- **Skip them** if your app doesn't use them.
- **Bring your own source**, your own label list for entities, or a contract-address list / an `eth_getCode`
  check for `is_contract`.
- **Layer them in** alongside your `token_holders` table at query time.

## Other ways to consume this data

The sink is the smoothest path for a holder list, but the **same data** is available however you prefer to build, all reading the one data lake:

- **Your existing message clients**, stream token transfers as they land via **Kafka**, **AMQP / RabbitMQ**, or
  **Amazon SQS** and maintain your own holder state.
- **REST / Arrow Flight**, read the decoded block stream directly (`GET /api/v1/continuum/{namespace}/{topic}`),
  with Arrow Flight (gRPC) for high-throughput pulls.
- **Your warehouse / notebook**, every feed is an Iceberg table; compute holders in **Snowflake, BigQuery,
  Spark, Trino, DuckDB, Pandas, or dbt** without moving data.

See the **Data Feeds API reference** and **protocol guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg).

## Field mapping reference

The **Fidelity** column shows how each value compares: **exact** (from the chain), **calculated** (from real
trades, very close), or **add yourself** (off-chain / chain-derived).

| `/erc20/:token_address/owners` | Data Feeds | Fidelity |
|---|---|---|
| `owner_address` | `token_holders.wallet_address` | exact |
| `balance` (raw) | `token_holders.balance` | exact |
| `balance_formatted` | derive: `balance / 10^decimals` (`token_metadata`) | exact |
| `usd_value` | `token_holders.usd_value` | calculated |
| `percentage_relative_to_total_supply` | derive: `balance / total_supply` (`token_metadata`) | exact |
| `totalSupply` (envelope) | `token_metadata.total_supply` | exact |
| `is_contract` | derive from chain / contract list | add yourself |
| `owner_address_label` | your own label source | add yourself |
| `entity`, `entity_logo` | your own entity source | add yourself |

## Good to know

- **Ranking is yours.** The endpoint returns biggest-first; with your own table, `ORDER BY balance DESC` (or
  `usd_value DESC`) gives the same, and you can rank or filter any other way too.
- **USD value comes from real trades**, very close to the endpoint, best compared with a tolerance; a
  thinly-traded token may value at 0.
- **`totalSupply`** from the endpoint envelope is best taken from `token_metadata` (the endpoint's own value can
  come back null).
- **Freshness**, holders are current-state on Postgres or MySQL. For real-time updates, follow the recipe
  README (ClickHouse is recommended for real-time and hybrid modes).
- **No per-call limit**, page through millions of holders with plain SQL.
