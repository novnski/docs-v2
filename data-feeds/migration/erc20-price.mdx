Moralis **Data Feeds** give you the complete, decoded onchain dataset, including a live USD and native mark for
every token, computed from real DEX trades. This guide moves your `/erc20/:address/price` integration onto Data
Feeds, so a token's price comes straight from that data lake, with **no per-call limits** and full control over
how you store, serve, and query it.

```
GET /erc20/:address/price
```

This is the single-token version of [ERC-20 token prices (batch)](/data-feeds/migration/erc20-prices), and it maps
the same way: the old endpoint's price is **already DEX-derived** (it names the exchange and pair it came from),
and Data Feeds computes its marks from those **same trades**. If you're pricing many tokens at once, use the
[batch guide](/data-feeds/migration/erc20-prices); everything below is that mapping for one token.

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however fits
your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**), **land it
with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery, Spark, DuckDB,
dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

For a single token's price on demand, the **sink** is the smoothest path, so we'll use it here. Because prices are
events, [streaming](#other-ways-to-consume-this-data) is also a great fit for a live single-token ticker.

## What to expect

You're moving from a single pre-packaged response to the **underlying data that produces it**, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model. For a token price:

**Comes through exactly**
- **The price source** (`pairAddress`, `exchangeName`/`protocol`) and **when it last changed**
  (`priceLastChangedAtBlock`, `blockTimestamp`), straight from the chain.
- **Token details** (`tokenName`, `tokenSymbol`, `tokenDecimals`), from the token contract.

**Calculated for you, from real trades**
- **Price** (`usdPrice`, `nativePrice`) comes from live onchain DEX activity, the same trades the old endpoint
  used, very close; compare with a small tolerance rather than expecting an identical figure.
- **24-hour change** (`24hrPercentChange`, `usdPrice24hr`, `usdPrice24hrUsdChange`) is a quick lookup of the price
  ~24 hours ago against the latest.
- **Pair liquidity** (`pairTotalLiquidityUsd`) comes from the pair's reserves priced in USD, add a pair recipe if
  you need it.

**Yours to control**
- **Which pair sets "the price."** When a token trades on several pairs, the old endpoint picked one (typically
  the deepest-liquidity pair); Data Feeds gives you every pair's mark, so you choose the rule.

**Add the extras you want**
- `tokenLogo`, `possibleSpam`, `verifiedContract`, and `securityScore` are off-chain signals, so they're not in
  the feed. Drop them, bring your own lists, or layer in a token list.

**Good to know**
- A token's mark comes from DEX activity, so a token that hasn't traded recently may carry a slightly older mark
  (on ClickHouse the recipe keeps the freshest mark per token for exactly this case).

## Before you begin

- A running Data Feeds **sink** writing to a database, see **Run a recipe** (quickstart). ClickHouse is
  recommended here for real-time pricing and the latest-mark lookup.
- The recipes below applied to that database.
- Your `MORALIS_API_KEY` and the chain you're pricing on.

<Note>
**Backfill is your choice here.** Prices are an *event list*, not current state. For "what's this token's price
**now**", you only need the feed running recently (the latest mark is enough). Index further back only if you want
historical prices (the old `to_block` behavior) or a longer 24-hour window. See
[History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipes

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| USD / native price + the pair it came from | `tokenPriceHistory` | `token_price_updates` |
| Token details (name, symbol, decimals) | `tokenMetadata` | `token_metadata` |
| Pair liquidity (`pairTotalLiquidityUsd`), optional | the `pairReserves` recipe | the pair's reserves |

`tokenPriceHistory` lands one row per price update per `(token, pair, protocol)`, the same DEX-derived mark the
old endpoint reported.

### Step 2: Query the latest price for the token

Take the newest mark for the token and join in its details:

```ts
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function getTokenPrice(token: string) {
  const { rows } = await pool.query(
    `SELECT DISTINCT ON (p.token_address)
            p.token_address, m.symbol, m.name, m.decimals,
            p.usd_price, p.native_price, p.pair_address,
            p.protocol AS exchange_name,
            p.block_number AS price_last_changed_at_block,
            p.block_timestamp
     FROM token_price_updates p
     LEFT JOIN token_metadata m ON m.token_address = p.token_address
     WHERE p.token_address = $1
     ORDER BY p.token_address, p.block_number DESC`,   -- newest mark
    [token.toLowerCase()],
  );
  return rows[0] ?? null;
}
```

That's it, you're pricing a token from a dataset you own, in real time, from the same DEX trades the old endpoint
used. For the 24-hour change fields and the multi-pair reference rule, follow the
[batch guide](/data-feeds/migration/erc20-prices#step-2-bring-it-together-in-one-view), it's the same logic applied
to one token.

### Step 3: Add the extras you want

`tokenLogo`, `possibleSpam`, `verifiedContract`, and `securityScore` are off-chain signals, so they're not part
of the onchain dataset. Skip them, bring your own token list for logos and your own allow/deny lists for spam and
verification, or layer them in from a dedicated metadata source.

## Other ways to consume this data

The sink is the smoothest path for on-demand pricing, but the **same feed** is available however you prefer to
build, all reading the one data lake:

- **Your existing message clients.** Point a **Kafka**, **AMQP / RabbitMQ**, or **Amazon SQS** consumer at Data
  Feeds and react to price updates as they land, a live single-token ticker without polling.
- **REST / Arrow Flight.** Read the decoded block stream directly, for Ethereum, namespace `0x1`, topic
  `master-4`:
  ```
  GET /api/v1/continuum/{namespace}/{topic}            # records by position range
  GET /api/v1/continuum/{namespace}/{topic}/schema     # the topic's Arrow schema
  ```
  Each record is a block carrying the decoded `tokenPriceUpdates` array the recipe projects from. Arrow Flight
  (gRPC) is the high-throughput option for large pulls.
- **Your warehouse / notebook.** Every feed is an Iceberg table, query price history straight from **Snowflake,
  BigQuery, Spark, Trino, Databricks, DuckDB, Pandas, or dbt** without moving data.

See the **Data Feeds API reference** and **protocol guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg) for
connection details.

## Field mapping reference

The **Fidelity** column shows how each value compares to the old endpoint: **exact** (from the chain),
**calculated** (from real trades, very close), or **add yourself** (off-chain signal).

| `/erc20/:address/price` | Data Feeds | Fidelity |
|---|---|---|
| `tokenAddress` | `token_price_updates.token_address` | exact |
| `usdPrice` / `usdPriceFormatted` | latest `token_price_updates.usd_price` | calculated |
| `nativePrice` | latest `token_price_updates.native_price` | calculated |
| `pairAddress` | `token_price_updates.pair_address` | exact |
| `exchangeName` | `token_price_updates.protocol` | exact |
| `exchangeAddress` | `pairAddressLookup.factory_address` (compose via the pair) | exact |
| `priceLastChangedAtBlock`, `blockTimestamp` | `token_price_updates.block_number` / `block_timestamp` | exact |
| `tokenName`, `tokenSymbol`, `tokenDecimals` | `token_metadata.*` | exact |
| `24hrPercentChange` / `usdPrice24hr*` | derive from price history | calculated |
| `pairTotalLiquidityUsd` | pair recipe (reserves x price) | calculated |
| `tokenLogo` | add yourself | off-chain |
| `possibleSpam`, `verifiedContract`, `securityScore` | add yourself | off-chain |

## Good to know

- **Same source as the old endpoint.** Both price from onchain DEX trades, so the marks line up closely, best
  compared with a small tolerance.
- **You choose the reference pair** when a token trades on several, giving you a stable, well-defined price.
- **Pricing many tokens?** Use the [batch guide](/data-feeds/migration/erc20-prices), one query, no 100-token cap.
- **Units.** `native_price` is a scalar (the old `nativePrice` was an object) and `block_timestamp` is in seconds
  (the old `blockTimestamp` was milliseconds), small shape adjustments when you map.
- **Freshness.** ClickHouse is recommended for real-time pricing and the latest-mark lookup; Postgres and MySQL
  carry the flat table (with the realtime reorg caveat, see the recipe README).
