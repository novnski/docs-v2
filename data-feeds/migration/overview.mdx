If you already call the Moralis Web3 Data API, these guides take you endpoint by endpoint onto **Data Feeds**.
You move from a pre-packaged REST response to the **underlying decoded data that produces it**, served from a
database you own, in real time, with no per-call limits and full control over how you store and query it.

Each guide is built around **one endpoint you already use**, and answers the only question that matters when
you switch: what happens to your exact response, field by field.

## Start with the model, once

Two concept pages explain how Data Feeds work, so every guide can link here instead of repeating it. Read
these first and the individual guides go quickly:

- [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) The one data lake, and the ways to consume it (your
  Kafka / AMQP / SQS clients, REST / Arrow Flight, the sink into your own database, or query engines via
  Iceberg).
- [Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) The fidelity model: a Data Feed
  **reconstructs** an endpoint from raw onchain data, it is not a byte-for-byte copy of the old response.

## How to read the fidelity of a migration

Every guide classifies each output value so you can plan with confidence. Throughout, you will see three
labels:

| Label | Meaning |
|---|---|
| **exact** | Comes straight from the chain, identical to the old endpoint (balances, transfers, metadata). |
| **calculated** | Derived from real onchain activity, for example USD prices from live DEX trades. Very close to the old value, best compared with a small tolerance. |
| **add yourself** | An off-chain signal (logos, spam flags, security scores) that is not in the lake. Bring your own source, or skip it. |

<Note>
**Decide your backfill before you start.** Some answers need full history to be correct (balances, holders,
approvals), others are correct at any window (swaps, transfers, logs, prices). Each guide states the answer
for its endpoint up front. See [History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Not yet covered

These are intentionally out of this set for now:

- **Solana endpoints** are parked while the Solana recipe and replica story is confirmed. The data exists on
  the Solana feed, but the recipes are not shipped yet.
- **Search and discovery endpoints** (`/tokens/search`, `/discovery/*`) are a search product rather than an
  indexed feed, so they are out of scope for a data-lake migration.
- **RPC node methods** (`eth_*`) belong to the node product, not Data Feeds.

## How each guide is structured

Every guide follows the same shape, so once you have read one you can skim the rest:

1. **How Data Feeds works**, and the best-fit way to consume this endpoint's data.
2. **What to expect**, your outputs grouped as comes-through-exactly, calculated-for-you, yours-to-control,
   and add-the-extras.
3. **Before you begin**, prerequisites and the backfill decision for this endpoint.
4. **Build it with the sink**, turn on the recipe(s), join them in a view, query from your app.
5. **Other ways to consume this data**, the same feed via Kafka / AMQP / SQS, REST / Arrow Flight, or Iceberg.
6. **Field mapping reference**, the per-field table with the fidelity label.
7. **Good to know**, the gotchas worth knowing before you ship.
