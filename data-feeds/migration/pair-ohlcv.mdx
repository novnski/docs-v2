Moralis **Data Feeds** give you the complete, decoded onchain dataset, including every DEX trade, so you can build
OHLCV candles for any pair from data you own. This guide moves your `/pairs/:address/ohlcv` integration onto Data
Feeds, so candlesticks come straight from that data lake, in real time, with **no per-call limits**, and at **any
timeframe** you like rather than a fixed set.

```
GET /pairs/:address/ohlcv
```

This is a clean migration: there's a **purpose-built OHLCV feed** that mirrors this endpoint, and because it's
built by aggregating the underlying trades, you own the trade-level data, so any timeframe or currency is a query,
not a fixed parameter.

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however fits
your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**), **land it
with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery, Spark, DuckDB,
dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

OHLCV is an aggregation over a pair's trades, so the **sink** is the smoothest path: land the trades, then bucket
them into candles.

## What to expect

You're moving from a single pre-packaged response to the **underlying data that produces it**, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model. For candles:

**Calculated for you, from real trades**
- **Open, high, low, close, and volume** are aggregated from the pair's onchain DEX trades (USD-enriched in-block),
  the same trades the old endpoint uses. They track it closely; compare with a small tolerance rather than
  expecting an identical figure.

**Comes through exactly**
- **The candle timestamp** and the **trade count** per candle are exact (the bucket bounds and a count).

**Yours to control**
- **Any timeframe, any currency.** The recipe ships 1-hour candles, but because you own the trade-level data, any
  granularity (1m, 5m, 1d) is a `GROUP BY`, and you can compute VWAP or other indicators from the same trades. No
  more being limited to a fixed timeframe parameter.

**Good to know**
- Candles come from DEX activity, so a thinly-traded pair has sparse candles (gaps where no trade occurred).
- The price is quoted in the pair's priced leg (the old endpoint's `tokenAddress`); be explicit about which token
  the OHLC is in.

## Before you begin

- A running Data Feeds **sink** writing to a Postgres (or MySQL) database, see the [quickstart](/data-feeds/migration/quickstart).
  ClickHouse is recommended for real-time candles.
- The recipe below applied to that database.
- Your `MORALIS_API_KEY` and the chain you're indexing.

<Note>
**Backfill the candle window you need.** Candles are built from trades, an *event list*, so you decide how far
back to index. For live candles, run the recipe `realtime`; for historical candles back to a date, backfill
`historical` / `hybrid` from that date. There's no requirement to index from genesis. See
[History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipe

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| A pair's trades (and a 1-hour candle surface) | `pairOhlcv` | `swaps` (one row per trade, USD-enriched) + a 1h candle surface |

`pairOhlcv` lands every trade for the pair (keyed by `pool_address`, priced in-block in USD) and buckets them into
1-hour candles, mirroring this endpoint. For 1h candles, read the candle surface directly.

### Step 2: Build candles at any timeframe

Because the `swaps` table is trade-level, you can bucket to any timeframe. Here's a 5-minute USD example, swap the
bucket size for 1m / 1h / 1d:

```sql
SELECT
  to_timestamp(floor(block_timestamp / 300) * 300)                       AS timestamp,    -- 300s = 5m
  (array_agg(price_usd ORDER BY block_number, log_index))[1]             AS open,
  max(price_usd)                                                         AS high,
  min(price_usd)                                                         AS low,
  (array_agg(price_usd ORDER BY block_number DESC, log_index DESC))[1]   AS close,
  sum(abs(notional_usd))                                                 AS volume,    -- abs: notional is signed on V3/V4
  count(*)                                                               AS trades
FROM swaps
WHERE pool_address = lower($1)
  AND block_timestamp BETWEEN $2 AND $3
GROUP BY timestamp
ORDER BY timestamp;
```

Use `60` / `3600` / `86400` for 1-minute / 1-hour / 1-day candles. That's it, you're serving OHLCV from a dataset
you own, at whatever granularity your chart needs, in real time.

## Other ways to consume this data

The sink is the smoothest path for candles, but the **same feed** is available however you prefer to build, all
reading the one data lake:

- **Your existing message clients.** Point a **Kafka**, **AMQP / RabbitMQ**, or **Amazon SQS** consumer at the
  pair's trades and update the current candle as each trade lands, real-time charts without polling.
- **REST / Arrow Flight.** Read the decoded block stream directly (`GET /api/v1/continuum/{namespace}/{topic}`),
  for Ethereum, namespace `0x1`, topic `master-4`. Arrow Flight (gRPC) is the high-throughput option.
- **Your warehouse / notebook.** Every feed is an Iceberg table, compute candles and indicators straight from
  **Snowflake, BigQuery, Spark, Trino, Databricks, DuckDB, Pandas, or dbt** without moving data, a natural home
  for time-series aggregation.

See the **Data Feeds API reference** and **protocol guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg) for
connection details.

## Field mapping reference

The **Fidelity** column shows how each value compares to the old endpoint: **exact** (from the chain) or
**calculated** (aggregated from real trades, very close).

| `/pairs/:address/ohlcv` | Data Feeds | Fidelity |
|---|---|---|
| `timestamp` | the time bucket | exact |
| `open`, `high`, `low`, `close` | first/max/min/last `swaps.price_usd` in the bucket | calculated |
| `volume` | `sum(swaps.notional_usd)` | calculated |
| `trades` | `count(*)` in the bucket | exact |
| `pairAddress` | `swaps.pool_address` | exact |
| `tokenAddress` (priced leg) | the quoted token | exact |
| `timeframe`, `currency` | your `GROUP BY` bucket + price leg | exact (your choice) |

## Good to know

- **A purpose-built feed mirrors this endpoint** for 1-hour candles; any other timeframe is a `GROUP BY` you own.
- **OHLC is trade-derived**, very close to the old endpoint (both come from DEX trades), best compared with a
  tolerance.
- **You own the trades**, so beyond candles you can compute VWAP, liquidity-weighted prices, or custom intervals.
- **Sparse candles** are expected on thinly-traded pairs (gaps where no trade occurred).
- **Freshness.** ClickHouse is recommended for real-time candles; Postgres and MySQL carry the trade table (with
  the realtime reorg caveat, see the recipe README).
