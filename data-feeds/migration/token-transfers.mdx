Moralis **Data Feeds** give you the complete, decoded onchain dataset, including every ERC-20 transfer, as a
real-time stream you own. This guide moves your `/erc20/:address/transfers` integration onto Data Feeds, so a
token's full transfer history comes straight from that data lake, with **no per-call limits** and full control
over how you store, query, and filter it.

```
GET /erc20/:address/transfers
```

This is the **by-contract** version of [Wallet ERC-20 transfers](/data-feeds/migration/wallet-erc20-transfers),
same data, same recipe, just filtered to a token instead of a wallet. Every onchain field comes through exactly;
the only extras you add are off-chain labels and display flags.

## How Data Feeds works

Data Feeds is a single service over one data lake of decoded onchain data, consume the **same data** however fits
your stack: stream it with your existing **Kafka / AMQP / SQS** clients (or **REST / Arrow Flight**), **land it
with the sink** into your own database, or **query it from your warehouse** (Snowflake, BigQuery, Spark, DuckDB,
dbt) via Iceberg. See [What are Data Feeds?](/data-feeds/concepts/what-are-data-feeds) for the full picture.

For a token's transfer history you query on demand, the **sink** is the smoothest path, so we'll use it here.
Because transfers are events, [streaming](#other-ways-to-consume-this-data) is also a great fit for live token
monitoring.

## What to expect

You're moving from a single pre-packaged response to the **underlying data that produces it**, see
[Data Feeds vs. the legacy API](/data-feeds/concepts/data-feeds-vs-the-legacy-api) for the general model. For token transfers:

**Comes through exactly**
- **The transfer** (`from_address`, `to_address`, `value`) and its **provenance** (`transaction_hash`,
  `block_number`, `block_timestamp`, `transaction_index`, `log_index`), straight from the chain.
- **Token details** (`token_name`, `token_symbol`, `token_decimals`), from the token contract.

**Yours to control**
- **Filters.** The same date, block, and ordering filters become plain query clauses; you scope to whatever
  window you want.

**Add the extras you want**
- `token_logo`, `possible_spam`, `verified_contract`, `security_score`, and the address `*_label` / `*_entity`
  fields are off-chain signals, drop them, bring your own lists, or layer in a token/label source.

**Good to know**
- There are **no USD prices** on this endpoint, so every onchain value comes through exactly, nothing to
  reconcile.
- High-volume tokens have enormous transfer histories; keyset-paginate on `(block_number, log_index)`.

## Before you begin

- A running Data Feeds **sink** writing to a Postgres (or MySQL) database, see the [quickstart](/data-feeds/migration/quickstart).
- The recipes below applied to that database.
- Your `MORALIS_API_KEY` and the chain you're indexing.

<Note>
**Backfill is your choice here.** Transfers are an *event list*, so you decide how much history to index. Run the
recipe `realtime` for a live feed of new transfers, or backfill `historical` / `hybrid` back to any date, for a
token's *complete* history, index from its deploy block. See [History & backfill](/data-feeds/concepts/history-and-backfill).
</Note>

## Build it with the sink (recommended)

### Step 1: Turn on the recipes

| What you need | Recipe | Table it keeps up to date |
|---|---|---|
| Every transfer (by token or by wallet) | `tokenTransfers` | `token_transfers` |
| Token details (name, symbol, decimals) | `tokenMetadata` | `token_metadata` |

`tokenTransfers` indexes both the token and the wallet sides, so a by-token lookup is fast.

### Step 2: Query a token's transfers

```ts
import { Pool } from 'pg';

const pool = new Pool({ connectionString: process.env.DATABASE_URL });

async function getTokenTransfers(token: string, limit = 100, before?: { block: number; logIndex: number }) {
  const { rows } = await pool.query(
    `SELECT t.*, t.amount / power(10, m.decimals) AS value_decimal
     FROM token_transfers t
     LEFT JOIN token_metadata m ON m.token_address = t.token_address
     WHERE t.token_address = $1
       AND ($2::bigint IS NULL OR t.block_number < $2)   -- keyset pagination
     ORDER BY t.block_number DESC, t.log_index DESC
     LIMIT $3`,
    [token.toLowerCase(), before?.block ?? null, limit],
  );
  return rows;
}
```

That's it, you're serving a token's full transfer history from a dataset you own, in real time, with no per-call
limits.

### Step 3: Add the extras you want

`token_logo`, `possible_spam`, `verified_contract`, `security_score`, and the address `*_label` / `*_entity`
fields are off-chain, so skip them, bring your own token and label lists, or layer them in from a metadata source.

## Other ways to consume this data

The sink is the smoothest path, but the **same feed** is available however you prefer to build, all reading the
one data lake:

- **Your existing message clients.** Point a **Kafka**, **AMQP / RabbitMQ**, or **Amazon SQS** consumer at the
  `tokenTransfers` stream and react to a token's transfers as they land, live token monitoring without polling.
- **REST / Arrow Flight.** Read the decoded block stream directly (`GET /api/v1/continuum/{namespace}/{topic}`),
  for Ethereum, namespace `0x1`, topic `master-4`. Arrow Flight (gRPC) is the high-throughput option.
- **Your warehouse / notebook.** Every feed is an Iceberg table, query transfer history straight from **Snowflake,
  BigQuery, Spark, Trino, Databricks, DuckDB, Pandas, or dbt** without moving data.

See the **Data Feeds API reference** and **protocol guides** (Kafka / AMQP / SQS / Arrow Flight / Iceberg) for
connection details.

## Field mapping reference

The **Fidelity** column shows how each value compares to the old endpoint: **exact** (from the chain) or **add
yourself** (off-chain). There's no calculated tier, this endpoint has no prices.

| `/erc20/:address/transfers` | Data Feeds | Fidelity |
|---|---|---|
| `address` (the token), `from_address`, `to_address` | `token_transfers.*` | exact |
| `value` | `token_transfers.amount` | exact |
| `value_decimal` | derive: `amount / 10^decimals` | exact |
| `transaction_hash`, `block_number`, `block_timestamp` | `token_transfers.*` | exact |
| `transaction_index`, `log_index` | `token_transfers.*` | exact |
| `block_hash` | from the block stream | exact |
| `token_name`, `token_symbol`, `token_decimals` | `token_metadata.*` | exact |
| `token_logo`, `possible_spam`, `verified_contract`, `security_score` | add yourself | off-chain |
| `from/to_address_label`, `*_entity`, `*_entity_logo` | add yourself | off-chain |

## Good to know

- **Same data as [wallet transfers](/data-feeds/migration/wallet-erc20-transfers)**, filtered by token instead of
  wallet.
- **No prices to reconcile**, every value is exact from the chain.
- **High-volume tokens** have large histories, paginate by `(block_number, log_index)`.
- **Filters are just SQL.** Date and block windows and `order` map to `WHERE` / `ORDER BY`.
- **Freshness.** Run the recipe `realtime` for a live feed; ClickHouse is recommended for real-time and hybrid
  modes.
